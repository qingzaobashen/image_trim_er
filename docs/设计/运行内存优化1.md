## 四、可能导致高内存占用的代码模块定位

### 4.1 【严重】UndoRedoManager — 完整 ImageData 快照存储

**文件：** [undoRedoManager.js](file:///d:/workT/wx_smallPrograms/pictureProcess/src/js/utils/undoRedoManager.js)

```javascript
// undoRedoManager.js:47-55 — 每次保存都存入完整 ImageData 快照
push(snapshot) {
    snapshot.timestamp = Date.now();
    this.history.push(snapshot);  // ← 不拷贝，直接存引用（可能被后续修改）
}

// imageProcessor.js:1303-1312 — 每次操作都创建完整快照
saveToHistory() {
    const snapshot = UndoRedoManager.createSnapshot({
        getImageData: () => canvasUtils.getImageData(this.mainCanvas),  // ← 16MB/64MB per snap
        getMask: () => new Uint8ClampedArray(this.currentMask),         // ← 4MB/16MB per snap
        getShadowMask: () => this.shadowMask ? new Uint8ClampedArray(this.shadowMask) : null,
        getEdgeData: () => this.edgeData ? new Uint8ClampedArray(this.edgeData) : null,
        // ...
    });
    this.undoRedoManager.push(snapshot);
}
```

**问题严重度评估：**
- 4096×4096 图片：单次快照 = 64MB + 16MB + 16MB + 16MB ≈ **112MB**
- maxHistory 动态调整为 3-20 步，最坏情况 = 20 × 112MB = **2.24 GB**
- `adjustMaxHistoryByImageSize` 限制到 256MB 总量，但 256/(64+16+16) ≈ **2-3步**，对 4K 大图几乎无撤销能力

### 4.5 【中等】AI 抠图过程中的临时对象堆积

**文件：** [smartCut.js:219-260](file:///d:/workT/wx_smallPrograms/pictureProcess/src/js/tools/smartCut.js#L219-L260)

```javascript
async applyAIRemoveBg() {
    // 1. Canvas → Blob（创建完整PNG编码的临时Blob，4096×4096 PNG ≈ 5-10MB）
    const blob = await new Promise((resolve) => {
        this.mainCanvas.toBlob(resolve, 'image/png');  // ← 临时Blob对象
    });
    const imageUrl = URL.createObjectURL(blob);          // ← 临时ObjectURL

    // 2. RawImage 加载（在WASM内存中创建另一个副本）
    const img = await RawImage.fromURL(imageUrl);        // ← WASM堆中像素副本

    // 3. 处理器预处理（创建张量副本）
    const processorResult = await processor(img);        // ← pixel_values张量
    pixel_values = processorResult.pixel_values;

    // 4. 模型推理（创建输出张量）
    const modelResult = await model({ input: pixel_values });
    outputTensor = modelResult.output;                   // ← output张量

    // 5. 后处理（创建maskData副本）
    const maskData = (await RawImage.fromTensor(...)).data; // ← 又一次拷贝

    // 6. 返回mask（再次拷贝）
    const mask = new Uint8ClampedArray(width * height);  // ← 最终mask
    
    // finally: pixel_values.dispose(); outputTensor.dispose(); ← 有清理但仅在finally
}
```

**在推理峰值时刻，同时存在的对象：**
- Canvas ImageData (64MB) + Blob (~5-10MB) + ObjectURL + RawImage(~16MB) + pixel_values(~16MB) + output(~16MB) + maskData(~16MB) + resultMask(16MB)
- **峰值叠加 ≈ 149-165 MB 额外内存**

### 4.6 【中等】OpenCV.js 动态加载及 ShadowProcessor 内存

**文件：** [shadowProcessor.js](file:///d:/workT/wx_smallPrograms/pictureProcess/src/js/tools/shadowProcessor.js)

- OpenCV.js (7.34MB) 按需加载，加载后在 WASM 堆中解压约 **15-25MB**
- ShadowProcessor 的 `detectEdges()` 和 `detectShadows()` 中含多次 `cv.imread()` / `cv.imwrite()` 调用，每次创建 cv.Mat 临时对象
- 需确认所有 cv.Mat 都有 `mat.delete()` 清理

## 七、优化方向和建议

### 7.1 高优先级（预期效果显著）

| 序号 | 优化方向 | 预期收益 | 实现方式 |
|------|----------|----------|----------|
| 1 | **增量快照替代全量快照** | 撤销历史内存降低 **60-80%** | 将 UndoRedoManager 改为只存储差异数据（操作类型+参数），而非完整 ImageData。撤销时从 `originImgBackup` 重放操作。 |
| 2 | **延迟释放 originImgBackup** | 释放 **16-64 MB** | 仅在噪点去除等需要恢复的操作前创建备份，操作完成后立即释放。或改为按需从 Canvas 读取。 |
| 3 | **合并 SelectionHistory 到 UndoRedoManager** | 释放 **4-16 MB/步** | 两个历史管理器功能重叠，统一到 UndoRedoManager，mask 作为快照的一部分存储一次。 |
| 4 | **Canvas → 张量直传，跳过 Blob** | 减少 **10-20 MB 临时峰值** | 使用 `canvas.getContext('2d').getImageData()` 直接构造 RawImage 或张量，绕过 `toBlob()` + `URL.createObjectURL()` 中间环节。 |

### 7.2 中优先级

| 序号 | 优化方向 | 预期收益 | 实现方式 |
|------|----------|----------|----------|
| 5 | **模型加载即用即弃** | 释放 **80-350 MB** | AI抠图完成后自动 `dispose()` 模型，下次使用再加载（已经缓存到浏览器 HTTP Cache，二次加载快）。 |
| 6 | **降低默认模型精度** | 减少 **40-80 MB** | 将默认模型从 RMBG-1.4 fp32 (168MB) 改为 q8 (42MB) — 实际上代码已这样设置，但确保 UI 不轻易引导用户切换。 |
| 7 | **brushCanvas 按需创建** | 减少 **16-64 MB** | BrushTool 的独立 brushCanvas 仅在画笔激活时创建，停用后释放。 |
| 8 | **mask 存储压缩** | 降低 **50-75%** | Uint8ClampedArray 按位存储（8 mask值→1字节），或对连续区域使用 RLE 编码。 |

### 7.3 低优先级

| 序号 | 优化方向 | 预期收益 | 实现方式 |
|------|----------|----------|----------|
| 9 | **大图分块(Tile)推理** | 降低峰值 ~30% | 将大图分割为 1024×1024 的瓦片分别推理后再拼接。 |
| 10 | **Web Worker 隔离** | 改善GC效率 | 将 AI 推理移到 Web Worker，利用 Worker 销毁时立即回收内存的特性。 |
| 11 | **强制 GC 提示** | 改善 GC 时机 | 在 AI 抠图完成后，调用 `performance.memory` API（Chrome特有）或触发 allocation pressure 提示浏览器尽早 GC。 |
| 12 | **OpenCV Mat 清理审计** | 防止泄漏 | 系统性审查所有 `cv.Mat` 创建点，确保 `delete()` 覆盖所有路径（含异常路径）。 |

## 八、总结

本产品 3.7GB 的峰值内存占用主要由以下因素叠加导致：

1. **AI 模型本身就大**（RMBG-1.4 fp32 文件 168MB，运行时膨胀至 ~350MB）
2. **全量快照的撤销系统**（undoRedoManager 每次保存完整 64MB ImageData + 多份 mask）
3. **数据冗余存储**（originImgBackup + 双份历史管理器 + 多个独立 Canvas）
4. **AI 推理临时对象堆积**（Blob → ObjectURL → RawImage → 张量 → maskData，6 层拷贝链）

**最有效的单点优化**是将撤销系统从全量快照改为操作日志重放模式，预计可将编辑过程中的内存占用降低 60-80%。结合模型即用即弃策略，可将峰值从 3.7G 降至约 **800MB-1.2GB**，显著改善用户体验。
